# Crucix 2.50.0 — Munkafolyamat a nehéz háttérmunkához / A worker process for the heavy background work

**Kiadás dátuma / Release Date:** 2026-10-15

---

## 🇭🇺 Magyar

- **Külön munkafolyamat.**
  - A szerver indításkor elindít egy gyerekfolyamatot: az exe-ből `crucix __worker`, forrásból `node scripts/cli.mjs __worker`. IPC-csatornán kommunikálnak.
  - A nehéz háttérmunka ott fut, egy másik processzormagon, így a szerver eseményhurka csak az eredményre vár.
  - **A munkafolyamatba került:**
    - a history-import a sweep-archívumokból;
    - a szálarchívum számolása;
    - a régi sorok átalakítása és a `VACUUM`;
    - a napi mentés és a megőrzés;
    - a témaelemzés;
    - a sweep új eseményeinek entitás-kinyerése (kb. 0,6 ms eseményenként).
  - **A szerverben maradt** az élő gráf linkelése és a szálak számolása, mert ezek a gráfot módosítják, amelyből az API olvas.
- **Tartalék.** Ha a munkafolyamat nem indul el, kilép vagy hibázik, a szerver 2 s és 60 s közötti várakozás után újraindítja. Addig ugyanazok a feladatok a szerverben futnak, ugyanúgy, mint eddig. Az állapot az `/api/health` válasz `worker` mezőjében látszik.
- **Mérés** az éles adatok másolatán, nehéz utólagos feldolgozás közben (teljes archívum-számolás, 126 s; import, 54 s; témaelemzés):
  - a válaszidő mediánja 7 ms, a p95 48 ms;
  - a 2.49-ben ugyanez 11 ms, 210 ms és egy 2,5 s-os maximum volt.

  A megmaradt kiugrásokat a sweep saját lépései (az események és a history írása, a kockázat, a gráf és a szálak) és a szerverben maradt gráf-visszatöltés okozzák.
- **Exe.** A munkafolyamat a buildelt exe-ből is működik: elindul, válaszol a pingre, és lefut benne a kinyerés és a témaelemzés.

## 🇬🇧 English

- **A separate worker process.**
  - At start-up the server starts a child process: `crucix __worker` from the executable, `node scripts/cli.mjs __worker` from source. They talk over an IPC channel.
  - The heavy background work runs there, on another CPU core, so the server's event loop only waits for the result.
  - **Moved to the worker:**
    - the history import from the sweep archives;
    - computing the thread archive;
    - rewriting the old rows and the `VACUUM`;
    - the daily backup and the retention;
    - the theme analysis;
    - entity extraction of a sweep's new events (about 0.6 ms an event).
  - **Kept in the server:** linking the live graph and computing the threads, because they change the graph that the API reads.
- **Fallback.** If the worker does not start, exits or fails, the server restarts it after a 2–60 s wait. Until then, the same jobs run in the server, just as before. The state shows in the `worker` field of `/api/health`.
- **Measured** on a copy of the live data during a heavy catch-up (a full archive computation, 126 s; the import, 54 s; the theme analysis):
  - median response time 7 ms, p95 48 ms;
  - in 2.49 the same was 11 ms, 210 ms and a 2.5 s maximum.

  The remaining spikes come from the sweep's own steps (writing the events and the history, risk, graph and threads) and from the graph backfill, which stays in the server.
- **Executable.** The worker also works from the built executable: it starts, answers ping, and runs the extraction and the theme analysis.
